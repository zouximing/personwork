## 1. 背景与问题

### 1.1 背景概述

本人任 IVD 仪器研发中心软件部副经理，主管部门开发工作。日常工作横跨"技术研发"与"部门管理"两条主线，具体包括七类工作（详见第 4 章）。这些工作来源异构（代码库、口头指派、会议、聊天消息、周期性事务）、节奏不同（每日高频、周期性、突发）、对象不同（任务、人、风险、文档），目前缺乏统一的汇集与管理手段，主要依靠记忆、聊天记录和零散文档。

同时，部门正在推进 AI 组织提效工作，当前处于 AI 基建阶段。个人工作台可作为 AI 能力落地的第一个真实内部应用：一方面自用验证提效效果，另一方面形成可复制、可推广给团队的方案样板。

### 1.2 核心痛点

| 编号 | 痛点 | 说明 |
|---|---|---|
| PP-1 | 任务分散、无统一视图 | 七类工作分布在不同渠道，缺少"今天该做什么"的单一视图，依赖记忆，易遗漏 |
| PP-2 | 委派事项跟丢 | 管理类工作大量是"交给别人、等回音"，缺乏对"等待中"事项的系统跟踪 |
| PP-3 | 周期总结费时 | 中心周总结/月总结需要翻聊天记录、回忆两周前的事情，素材没有在日常沉淀 |
| PP-4 | 产线重点与风险后知后觉 | 三条产线的月/周重点任务进展以口头、群消息汇报为主，缺乏结构化跟踪与超期预警；风险问题闭环情况难以回顾 |
| PP-5 | MR 评审积压 | 待评审 MR 无统一入口，需反复登录 GitLab 查看，存在漏审和积压 |
| PP-6 | 管理记录不成体系 | 人员 1:1、招聘跟进等散落在笔记本和聊天记录中，无法回溯 |

### 1.3 建设机会

个人工作台与部门 AI 提效工作可以互相成就：工作台的开发过程是 AI 辅助编程的实践案例，运行时接入公司 AI 基建的模型能力，自用见效后向团队推广，形成"基建 → 应用 → 反馈"的闭环。

## 2. 目标与非目标

### 2.1 建设目标（第一期）

| 编号 | 目标 | 对应痛点 |
|---|---|---|
| G-1 | 统一任务中心：七类工作统一录入、分类、跟踪 | PP-1 |
| G-2 | 每日工作视图：今日待办、进行中、等待他人、临期/超期一目了然 | PP-1、PP-2 |
| G-3 | 记录自动沉淀，周/月总结一键生成素材初稿 | PP-3 |
| G-4 | GitLab MR 待评审自动同步与积压提醒 | PP-5 |
| G-5 | 产线重点与风险看板：三条产线的**月重点、周重点任务进展跟踪** + 风险登记与闭环 | PP-4 |
| G-6 | 架构预留团队化：数据模型支持多用户，二期可推广给团队 | — |

### 2.2 非目标（第一期明确不做）

1. 不替代公司正式系统：GitLab、项目管理平台、HR 系统仍是数据源头，工作台定位为"个人汇集、视图与提醒层"，通过链接引用关联，不做业务数据双向同步。
2. 不做移动端 App，仅做桌面浏览器页面（移动端网页适配放二期）。
3. 不做多用户权限体系（一期单用户；数据模型预留字段）。
4. 不做自动化代码评审（MR 功能仅覆盖"评审任务管理"，不评审代码内容）。

## 3. 用户与典型场景

### 3.1 用户定义

一期仅一个用户：本人（管理员角色）。二期潜在用户：部门同事、产线负责人（只读或受限编辑）。

### 3.2 典型使用场景

| 编号 | 场景 | 描述 |
|---|---|---|
| S-1 | 每日开工 | 早上打开工作台首页：查看今日待办、临期/超期、等待超期事项，确定今日三件要事 |
| S-2 | 快速捕获 | 开会中/被打断时，10 秒内把临时事项记入"收件箱"，会后统一整理归类 |
| S-3 | MR 评审 | 首页看到待评审 MR 列表（含停留天数），点链接跳转 GitLab 评审，回来勾选完成，自动计入当日工作记录 |
| S-4 | 委派跟踪 | 把任务标记"等待他人"，登记等待对象与预期回复日；对方超期未回复时首页预警 |
| S-5 | 周五写周总结 | 一键导出本周完成事项（按工作域分组）的 Markdown 初稿，产线进展自动单独成节，在此基础上人工加工成中心周总结 |
| S-6 | 月初产线重点规划 | 为三条产线分别登记本月重点任务（含目标/交付物、负责人），可由上月未完成项一键结转 |
| S-7 | 产线周例会 | 逐条过各线本周重点，更新进展状态（正常/有风险/受阻/完成）与进展说明，登记/更新风险项；受阻与有风险项自动进入周报素材 |
| S-8 | 招聘跟进 | 更新候选人阶段，登记明日面试，面试前收到提醒 |
| S-9 | 管理记录 | 1:1 之后记录要点与待办，下次 1:1 前可回溯 |

## 4. 业务域梳理

七类工作归为三大类、七个业务域，统一在"任务"主模型上扩展：

| 大类 | 业务域 | 主要内容 | 任务来源 | 频率 | 管理诉求 |
|---|---|---|---|---|---|
| 执行类 | D1 研发任务 | 软件功能实现、Bug 修改 | 项目平台需求单/缺陷单、GitLab Issue | 每日 | 进度、优先级、关联代码 |
| 执行类 | D2 代码评审 | 本地 GitLab MR 评审 | GitLab 自动同步 | 每日多次 | 不漏审、不积压 |
| 推动类 | D3 提效与 AI 基建 | 部门平台提效、AI 组织提效、AI 基建项目 | 部门目标分解、自规划 | 每周 | 里程碑进度、汇报素材 |
| 管理类 | D4 人员管理 | 1:1、绩效、培养、团队事务 | 主动安排 + 突发 | 每周 | 记录沉淀、待办跟进 |
| 管理类 | D5 招聘 | 岗位需求、候选人跟进、面试安排 | HR、内推 | 每周 | 阶段流转、时间提醒 |
| 管理类 | D6 产线管控 | 三条产线任务管理：重点跟踪各产线**月重点、周重点任务进展**，辅以风险管控（具体执行由产线负责人负责） | 产线例会、产线负责人上报 | 每周 | 重点任务进展可视、风险等级、责任到人、闭环 |
| 管理类 | D7 经理协助事务 | 中心周总结、月总结及其他指派 | 经理指派 + 周期性 | 每周 | 周期提醒、素材积累 |

### 4.1 建模原则

1. **一套任务主模型**：所有域共用统一任务结构（见 FR-01），差异通过"工作域 + 扩展属性"表达，避免七套表单七套逻辑。
2. **D2/D5/D6 用专用视图增强**：MR、候选人、产线重点/风险在任务主模型之上提供专用列表/看板，因其字段与流程有特殊性。
3. **人作为一等对象**：D4/D5 都涉及"人"（下属、候选人），人员档案独立建表，任务可关联人。
4. **周期化结构（D6 专用）**：产线重点按"产线 × 周期（月/周）× 重点条目"建模，进展随周期滚动更新，天然支持回溯与对比。

## 5. 功能需求

优先级定义：**P0** = 第一期必须；**P1** = 第一期尽量（可裁剪）；**P2** = 二期。

### 5.0 主动补充能力一览

以下能力是整理需求时主动补充的（非七类工作原始描述直接要求），已在对应章节体现，评审时请重点确认取舍：

| 补充能力 | 对应需求 | 补充理由 |
|---|---|---|
| 快速捕获收件箱 | FR-02 | 任务系统能否长期用下去，取决于录入是否足够快（目标 ≤10 秒） |
| 四象限优先级 | FR-04 | 管理岗应先分"重要"再排"紧急"，防止被紧急杂事淹没 |
| 今日三件要事 | FR-06 | 每日聚焦，防止日程被杂事填满 |
| "等待他人"状态强化 | FR-03 | 委派跟踪是管理岗核心场景，必填等待对象与预期回复日 |
| 素材库 | FR-15 | 写总结时"随手标记"远优于"期末回忆" |
| 时间分布统计 | FR-11 | 管理者自省：时间实际花在七类工作上的比例 |
| AI 辅助三件套 | FR-29~31 | 与 AI 提效工作协同，工作台成为 AI 基建的首个应用场景 |
| 团队化预留 | NFR-05 | 二期平滑推广给团队，避免返工 |

### 5.1 任务管理核心

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| FR-01 | 任务模型与录入 | P0 | 属性：标题、描述、所属工作域（D1~D7）、优先级、状态、截止日期、开始日期、关联人、标签、来源链接（需求单/MR/文档 URL）、创建/完成时间 |
| FR-02 | 快速捕获收件箱 | P0 | 提供全局快捷入口（网页快捷键 + 一键捕获页），仅填一句话即入收件箱，会后统一整理归类；录入耗时目标 ≤10 秒 |
| FR-03 | 状态流转 | P0 | 收件箱 → 待办 → 进行中 → 等待他人 → 已完成/已取消。转"等待他人"时必填：等待对象、等待内容、预期回复日期 |
| FR-04 | 四象限优先级 | P0 | 重要/紧急两维标记，提供四象限视图，而不只有单一紧急度 |
| FR-05 | 每日工作台首页 | P0 | 分区展示：今日要事、今日待办、进行中、等待他人（标注是否超期）、临期/超期、收件箱未整理数、待评审 MR 数、产线高风险/受阻项 |
| FR-06 | 今日三件要事 | P0 | 每天从待办中最多指定 3 件"要事"，首页置顶 |
| FR-07 | 周期任务 | P0 | 按模板周期自动生成任务（如每周五"中心周总结"、每月末"月总结"、每周"产线例会"） |
| FR-08 | 提醒 | P0 | 截止日临近（提前量可配置）、超期、等待他人超期提醒；应用内提醒条 + 可选 Windows 系统通知 |
| FR-09 | 任务归档 | P1 | 已完成任务自动归档（默认隐藏、可查），保持列表清爽 |

### 5.2 视图与统计

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| FR-10 | 分域看板/列表 | P0 | 按七个业务域过滤，看板（按状态分列）与列表两种展示 |
| FR-11 | 周/月视图与统计 | P0 | 按周/月查看完成情况；统计各工作域任务量与耗时占比（时间都花在哪） |
| FR-12 | 全文搜索 | P0 | 标题/描述/备注全文检索 |

### 5.3 周报/月报生成

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| FR-13 | 周报素材初稿 | P0 | 一键导出指定周期内完成事项，按工作域分组生成 Markdown 初稿（含关键任务、进展、风险）；产线进展依据月/周重点数据自动单独成节（见 FR-25） |
| FR-14 | 总结模板配置 | P1 | 支持自定义导出模板（分组方式、字段、格式），适配中心总结的固定格式 |
| FR-15 | 素材库 | P1 | 随手把某条任务/一段文字标记为"总结素材"，导出时自动汇总 |

### 5.4 GitLab MR 评审同步

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| FR-16 | 待评审 MR 同步 | P0 | 通过 GitLab API 定时拉取"我评审中"的 Open MR：标题、项目、分支、作者、提交时间、评审停留时长；支持按项目过滤 |
| FR-17 | MR 与工作记录联动 | P0 | 评审完成的 MR 自动生成一条已完成任务（域=D2），计入当日记录并进入周报统计；也可手动从 MR 创建跟踪任务 |
| FR-18 | 积压提醒 | P0 | 评审停留超过阈值（可配置，默认 2 天）的 MR 在首页预警 |

### 5.5 产线重点与风险看板（三条产线）

产线模块的两个核心：**月重点/周重点任务进展跟踪**（主）+ **风险登记与闭环**（辅）。定位是"本人对三条产线的管控视图"，具体执行由各产线负责人负责。

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| FR-19 | 产线总览 | P0 | 三条产线各一张概况卡片：本月重点完成率、本周重点进展状态分布（正常/有风险/受阻/完成）、开放风险数（按等级着色），点击进入单产线详情 |
| FR-20 | 月重点任务 | P0 | 每条产线每月登记重点任务（建议每线 ≤5 条，聚焦）：描述、目标/交付物、负责人、状态（未开始/进行中/受阻/已完成/取消）、完成度、备注；支持从上月未完成项一键结转 |
| FR-21 | 周重点任务与进展跟踪 | P0 | 每周为各产线登记周重点（可关联所属月重点，也允许独立事项），字段：描述、关联月重点、负责人、本周目标、进展状态（正常/有风险/受阻/已完成）、进展说明、更新时间；按周切换查看，支持与上周对比、自动标出上周遗留项 |
| FR-22 | 进展更新提醒与周期管理 | P0 | 每周固定日（默认周五）提醒更新各线周重点进展；月末自动汇总各线月重点完成率；新周期开始时提示初始化（结转/新建） |
| FR-23 | 风险登记册 | P0 | 风险条目：所属产线、描述、等级（高/中/低）、影响、负责人、缓解措施、目标闭环日期、状态（开放/跟踪中/已闭环）、是否升级 |
| FR-24 | 风险预警 | P0 | 高等级风险、超期未闭环风险在首页与产线视图飘红；支持按产线/等级过滤 |
| FR-25 | 产线进展进周报 | P0 | 导出周报素材时，"产线进展"自动成节：各线本周重点完成情况、受阻/有风险项、风险项变化（新增/闭环） |

### 5.6 招聘与人员管理

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| FR-26 | 招聘看板 | P1 | 岗位需求（名称、HC 数、状态）+ 候选人阶段流转（简历筛选/初面/复面/终面/Offer/入职/淘汰），每阶段可记备注 |
| FR-27 | 面试提醒 | P1 | 面试安排登记后，面试前一天/前一小时提醒 |
| FR-28 | 人员档案 | P1 | 轻量人员档案：基本信息、1:1 记录（日期 + 要点 + 待办）、关键事件；任务可关联人。敏感数据，本地存储（见 NFR-02） |

### 5.7 AI 辅助（与 AI 提效工作协同）

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| FR-29 | AI 周报成稿 | P1 | 在 FR-13 素材初稿基础上，调用 LLM 生成连贯的总结文字稿（可编辑修订），对接公司 AI 基建的模型网关 |
| FR-30 | 自然语言录入 | P2 | 一句话自动解析为结构化任务（识别截止时间、域、优先级），如"明天下午前给张三回复性能测试结论" |

## 6. 非功能需求

| 编号 | 类别 | 需求 |
|---|---|---|
| NFR-01 | 部署形态 | 本地 Web 应用：服务跑在本机（Windows）或内网服务器，浏览器访问；提供一键启动/停止脚本 |
| NFR-02 | 数据安全 | 全部数据本地/内网存储，人员与招聘等敏感信息不落任何第三方云端；一期即设置访问口令（哪怕单用户）；数据库文件级访问控制 |
| NFR-03 | 使用效率 | 新任务录入（含快捷入口）≤3 步、≤10 秒；首页打开 ≤2 秒（本地） |
| NFR-04 | 性能 | 万级任务、千级 MR/产线记录下列表与搜索流畅（<1 秒） |
| NFR-05 | 可扩展（团队化预留） | 核心数据表预留 user_id 与权限字段；API 无状态、带鉴权框架（一期可简化为单令牌）；为二期多人使用留平滑升级路径 |
| NFR-06 | 数据开放 | 数据库（SQLite 起步）+ 开放导出格式，任何时候可整体迁走 |
| NFR-07 | 可推广性 | 提供部署文档与初始化脚本，同事可低成本复制一套自用（二期推广的基础） |
| NFR-08 | 可维护性 | AI 辅助开发为主，代码与文档同步维护，作为部门 AI 辅助开发的示范项目 |

## 7. 技术形态与架构建议

### 7.1 形态结论（已确认）

采用**本地 Web 应用**：后端服务 + 数据库部署在本机或内网服务器，浏览器访问。

| 维度 | 本地 Web（选定） | Qt 桌面 | 现成工具（Obsidian/多维表格） |
|---|---|---|---|
| 团队推广 | 好：同事浏览器直接访问，零安装 | 需分发安装包 | 每人自行搭建，难统一 |
| AI 集成 | 好：服务端直接调 LLM/AI 基建 | 需自行封装 | 受工具能力限制 |
| GitLab 集成 | 好：服务端定时任务 | 可做但繁琐 | 依赖插件，不可控 |
| 敏感数据 | 好：本地/内网自控 | 好：完全本地 | 部分工具云端同步有风险 |
| 开发效率 | 高（AI 辅助下界面迭代快） | 中（界面开发量偏大） | 最高但定制天花板低 |

### 7.2 参考架构（建议）

```
浏览器（Vue3/React + 组件库，如 Element Plus / Ant Design）
        │ HTTP/JSON（鉴权：一期单令牌，预留 JWT）
后端服务（建议 FastAPI（Python），或 Node.js/NestJS）
        │
        ├── 任务/视图/统计/导出 API
        ├── 产线模块（月/周重点、进展、风险登记册）
        ├── GitLab 集成模块（定时同步 MR，API Token）
        ├── LLM 接口层（对接公司 AI 基建模型网关；未就绪时功能降级）
        └── 数据层：SQLite（起步，单文件易备份）→ 团队化时平迁 PostgreSQL
```

核心数据对象初想：任务（主表）、任务域、人员档案、候选人、产线、产线重点条目（周期类型 月/周 + 所属周期 + 进展记录）、风险条目、MR 缓存、总结素材、系统配置。

说明：
1. 技术栈（FastAPI + Vue3）为建议项，开发时最终评估，需求文档不做强约束。
2. SQLite 起步零运维、单文件备份；多用户预留通过 user_id 字段与 ORM 迁移机制保证，二期切 PostgreSQL。
3. 产线重点条目的"进展记录"按周期版本化保存（每周一条快照），支持回溯任意周的进展状态。

### 7.3 与 AI 提效工作的关系

个人工作台定位为 AI 基建的**第一个内部应用场景**：

1. 开发过程采用 AI 辅助编程，产出可度量的提效案例（开发耗时、代码量），作为部门 AI 提效的实证素材；
2. 运行时接入公司模型网关，验证基建能力（鉴权、限流、Prompt 管理）在真实应用上的表现；
3. 自用 → 部门内推广 → 沉淀为团队共用平台，形成"基建 → 应用 → 反馈"闭环。

## 10. 附录

### 10.1 术语表

| 术语 | 含义 |
|---|---|
| MR | Merge Request，GitLab 合并请求 |
| 收件箱 | 未整理的快速捕获任务暂存区（GTD 方法） |
| 等待他人 | 已委派/待对方回复的任务状态，管理岗跟踪委派事项的核心状态 |
| 月重点/周重点 | 产线按月/按周期设定的重点任务条目，带进展状态滚动跟踪 |
| 风险登记册 | 产线风险的结构化台账（等级、负责人、闭环跟踪） |
| 四象限 | 重要 × 紧急两维的优先级划分 |
| AI 基建 | 部门 AI 组织提效工作中的基础设施阶段（模型网关、鉴权等） |

### 10.2 方法论参考

任务模型借鉴 GTD（收件箱/整理/回顾）与管理者日程实践（要事优先、等待清单、周回顾）；产线月/周重点采用"周期化目标 + 滚动进展"模式；周报生成遵循"记录即总结"（日常沉淀替代期末回忆）。
