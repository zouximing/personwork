# Windows 与 Linux 部署说明

日期：2026-11-07。Windows 为当前开发验证环境；Linux 为待实机验证的部署准备。

## 一、部署取舍

第一阶段采用 Windows 本机浏览器＋Node 后台，减少安装和运行组件。SQLite 使用后台本机磁盘；浏览器只通过 HTTP API 访问，业务代码和数据分离。

第二阶段采用 Linux 上单个 Node 服务同时提供 Web 静态文件与 API。Windows 浏览器访问同一 Origin，使用 HTTPS 与访问口令。首版提供直接 TLS 模式，不要求数据库服务器、不使用网络共享 SQLite、不默认开放公网。访问口令使用受保护文件，凭据在后台加密保存。

网络前提发生变化：当前公司电脑能访问来源，不等于 Linux 能访问。Linux 上的后台必须能解析并连接 PingCode、GitLab 和内部模型；Windows 浏览器打开来源原链接仍需自己的访问权限。三类模型分别验证实际服务、协议、路由及资料许可。

## 二、Windows

1. 安装 Node.js 24；在工程目录运行 `npm ci`、`npm run build`，设置 `WORKBENCH_DATA_DIR` 后运行 `npm start`。本机已验证目录为 `D:\project\personalwork-codex-data`，启动命令见README。
2. 打开 `http://127.0.0.1:4310`。若换端口，Origin 应与浏览器访问地址一致。默认不要换用 localhost 别名。
3. 数据默认在 `%LOCALAPPDATA%\PersonalWorkbench`，可用 `WORKBENCH_DATA_DIR` 指向专用本机目录。工作文件不要直接放在该目录内混用。
4. 凭据通过设置界面更换／清除，不写环境变量明文。Windows 主密钥由 DPAPI CurrentUser 保护，运行账号变化时需使用可移植备份迁移并重录凭据。
5. `npm start` 进程持续运行时才有后台同步。当前没有安装开机服务或系统计划任务。

本环境默认 LOCALAPPDATA 目录的新文件同目录rename返回EXDEV，原子快照无法完成，底层原因尚未确定。已保留原目录，并使用仓库外专用目录；该目录的新建/rename/覆盖替换/读回及应用保护快照均实测成功。不是通过先删除、复制覆盖或跳过加密来规避失败。

只修改非敏感运行目录的示例：

```powershell
$env:WORKBENCH_DATA_DIR = 'D:\PersonalWorkbenchData'
npm start
```

后台输出启动地址及通用启动错误，不开启请求正文日志。不要将整个环境变量、配置文件或接口原始响应粘贴到诊断日志。

## 三、Linux 准备

建议专用低权限账号 `personal-workbench`。应用目录 `/opt/personal-workbench`，数据 `/var/lib/personal-workbench`，密钥与 TLS 材料放 `/etc/personal-workbench`。具体服务器地址、账号和路径在实际部署时替换。

安装同一受支持 Node.js 24，使用锁定依赖 `npm ci` 并执行 `npm run check`。原生 SQLite 模块若无对应预编译包，需要该发行版的本机编译工具；Windows 的 node_modules 不可直接复制到 Linux。

主密钥只在目标服务器本地产生，传入的是绝对路径，不是密钥本体：

```bash
WORKBENCH_MASTER_KEY_FILE=/etc/personal-workbench/master.key npm run setup:linux-key
```

脚本仅在 Linux 运行，以独占创建方式生成 32 字节密钥，不覆盖已有文件、不输出内容。父目录需由管理员预先创建；文件由服务账号所有，权限 0600，目录 0700。TLS 私钥、访问口令文件同样仅服务账号可读。访问口令至少 16 字符，使用目标机安全录入方式创建，勿放进 shell 命令历史。不要复用文档示例口令。

## 四、Linux 环境文件与服务

将以下非敏感路径配置保存为 `/etc/personal-workbench/service.env`，替换实际内网域名。环境文件本身不包含 Token 或访问口令：

```ini
WORKBENCH_HOST=0.0.0.0
WORKBENCH_PORT=4310
WORKBENCH_ORIGIN=https://workbench.intranet:4310
WORKBENCH_DATA_DIR=/var/lib/personal-workbench
WORKBENCH_OUTPUT_DIR=/var/lib/personal-workbench/artifacts
WORKBENCH_MASTER_KEY_FILE=/etc/personal-workbench/master.key
WORKBENCH_PASSWORD_FILE=/etc/personal-workbench/access-password
WORKBENCH_TLS_CERT=/etc/personal-workbench/server.crt
WORKBENCH_TLS_KEY=/etc/personal-workbench/server.key
```

TLS 证书必须匹配实际浏览器访问域名，并被工作电脑信任。实际证书取得和信任方式按公司环境配置，程序不绕过证书校验。不满足 HTTPS、准确 Origin 或口令配置时，远程启动拒绝。

systemd 模板（Node 绝对路径按安装实际位置调整）：

```ini
[Unit]
Description=Personal Workbench
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=personal-workbench
Group=personal-workbench
WorkingDirectory=/opt/personal-workbench
EnvironmentFile=/etc/personal-workbench/service.env
ExecStart=/usr/bin/node /opt/personal-workbench/apps/server/dist/index.js
Restart=on-failure
RestartSec=5
TimeoutStopSec=60
UMask=0077
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/var/lib/personal-workbench

[Install]
WantedBy=multi-user.target
```

模板作为部署准备交付，没有安装或启动任何公司服务。实际发布前检查依赖、文件所有权、证书、受限目录、进程停止、重启恢复、浏览器登录及来源网络。

## 五、迁移及回退

1. 在 Windows 停止新执行和同步，导出口令加密备份，另备份产物目录；核对导出成功和文件位置。
2. 在 Linux 建立新私有数据目录和独立密钥，启动空服务，通过 Windows 浏览器登录。
3. 恢复 `.pwb`，核对任务、提示词、月周重点、来源关联、回顾历史；不要复制 Windows DPAPI 密钥文件。
4. 重新录入两处来源及各模型凭据，保持同步停用，先分别测试身份／读取／模型文字及工具能力。
5. 核对旧回写和执行记录，不自动恢复已发出操作。确认后逐项启用同步；PingCode 状态写仍受能力门禁。
6. 原 Windows 数据目录保留作为回退副本，避免两端同时写入成为分叉数据源。此版本不提供双向跨设备数据库合并。

回退应用版本前先备份数据。数据库版本比程序支持版本更高时拒绝打开；不要通过手工删除版本号绕过。恢复动作会建立原库保护快照，失败时原事务回滚。
