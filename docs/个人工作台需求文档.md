# 个人工作台需求文档

版本：v0.7（补充 PingCode 与 GitLab 设置，待评审）  
日期：2026-11-07  
调整依据：工作归入“个人任务”和“管理”两个方向；PingCode 与 GitLab 均为公司内网本地部署；首版纳入同步与受控回写、MR 专项视图、常用提示词保存／编辑／复制，以及支持本地部署、DeepSeek 官方服务、New API 的 AI 辅助与任务执行。  
当前阶段：需求梳理，尚未进入产品开发。

## 1. 产品定位与工作分类

个人工作台服务于每天的工作安排、执行、跟进和回顾。重点做好两件事：推进本人承担的任务，以及掌握三个产线的月周重点进展和风险。

### 1.1 两个主分类

| 主分类 | 包含内容 | 建设重点 |
| --- | --- | --- |
| 个人任务 | 从内网 PingCode 拉取的软件功能、Bug、平台提效与 AI 基建任务；从内网 GitLab 拉取的 MR 评审建议一并纳入 | 展示来源编号，在来源任务与 MR 基础上安排今日工作、下一步、跟进和结果 |
| 管理 | 产线管理，以及人员、招聘、经理协同等其他管理事项 | 优先做好三个产线的月重点、周重点、进展偏差和风险；其他事项轻量跟进 |

“管理”下面只保留两个分组：

- **产线管理：重点。** 看三个产线本月和本周要交付什么、进展如何、哪里有偏差、是否需要本人协调。
- **其他管理事项：轻量。** 人员沟通、招聘、经理交办及中心周月总结共用一套任务机制，以标签区分。

部门平台提效与 AI 基建作为个人任务中的项目或专题推进，不再单设顶层模块。MR 评审归入个人任务是本稿建议，可按类型筛选；其评审状态和版本信息按需展开。

用户已明确两个来源均部署在公司内网：研发等个人任务主要从本地部署的 PingCode 拉取，保留任务编号；MR 合并请求评审从本地部署的 GitLab 拉取，保留所属项目及 MR 编号。工作台补充个人安排与跟进，不要求重复录入。少量临时事项可本地补充；GitLab MR 不要求已有 PingCode 任务编号。

### 1.2 产品重点

本人执行的功能实现、Bug 修改、平台提效，以及三个产线的重点进展是首版核心。AI 辅助、任务执行和提示词库作为共用能力服务于这两个方向。

首页呈现个人今日重点，同时让产线本周偏差和高风险直接可见；具体布局在原型阶段确认，按事项紧急程度、计划和本人选择安排展示。

### 1.3 原有场景的归并

| 原有工作内容 | 新归属 | 呈现方式 |
| --- | --- | --- |
| 软件功能实现、Bug 修改 | 个人任务 | 主要任务类型 |
| GitLab MR 评审 | 个人任务（建议） | 从内网 GitLab 拉取，以评审类型呈现，可关联 PingCode 任务 |
| 部门平台提效、AI 基建 | 个人任务 | 长期项目／专题，可拆解里程碑与行动 |
| 三个产线的月周重点、风险跟踪 | 管理 → 产线管理 | 管理侧的核心视图 |
| 人员管理、招聘、经理协同与中心周月总结 | 管理 → 其他管理事项 | 统一待办、跟进和周期事项，不建设独立业务系统 |

这些场景用于说明覆盖范围，不再对应多个并列功能模块。

## 2. 核心目标与首版范围

### 2.1 核心目标

1. **知道今天先做什么。** 个人任务有重点、有下一步，临时插单后可以调整安排。
2. **知道产线重点推进到哪里。** 月目标与周阶段结果能关联，对照计划查看实际进展。
3. **知道哪些事项需要介入。** 等待反馈、进展偏差、阻塞及风险能够及时进入关注范围。
4. **减少重复整理。** 日常进展与结果可用于个人回顾及中心周月总结。
5. **保持使用轻便。** 小任务快速记，重点事项按需补充，普通管理事项不引入复杂流程。

### 2.2 首版范围

| 能力 | 首版做到什么 |
| --- | --- |
| 今日工作台 | 个人今日重点、待处理和待跟进事项，以及产线本周偏差与关键风险 |
| 来源设置 | 分别配置 PingCode 与 GitLab 的内网地址、认证、项目／拉取范围及同步规则，保存配置、测试连接并查看结果 |
| 个人任务 | 从内网 PingCode 拉取任务并在确认范围内回写；从内网 GitLab 只读同步 MR，识别新提交并提供专项视图；保留个人安排 |
| 产线管理 | 三个产线的月重点、周重点、负责人反馈、偏差、协调动作、风险与结转 |
| 其他管理事项 | 用普通任务记录人员、招聘、交办、总结等事项，支持等待与跟进 |
| AI 辅助与任务执行 | 拆解任务、生成总结，并通过已接入工具执行授权范围内的具体行动；有执行计划、过程、产物和核验结果 |
| 模型接入 | 支持本地部署模型、DeepSeek 官方 API、New API 网关，保存多套配置，按实际能力选择文本生成或任务执行 |
| 常用提示词库 | 新建、编辑、保存、查找并复制提示词正文；下次打开继续使用，可选填入 AI 指令 |
| 回顾与数据 | 周月材料整理、人工编辑与导出、可靠保存、备份恢复，以及同步／回写结果追踪 |

不再为人员、招聘、平台提效分别建设独立业务模块。MR 专项视图位于个人任务内；AI 操作融入任务、执行记录与回顾；提示词库是共用工具入口。完整代码评审操作继续在公司 GitLab 中进行。

首版必须覆盖两处来源接入、PingCode 受控回写、MR 变化跟进、提示词库、三类模型接入及真实 AI 任务执行；本地录入、手工总结和模型生成文字不能代替相应接入或执行验收。GitLab 保持只读，不在工作台发布意见、批准或合并 MR。

“高级同步或自动化”包括定时拉取、变化识别、回写结果跟踪、安全重试与冲突处理；AI 按明确的任务类型调用已注册工具完成执行。具体周期、回写字段、执行场景和授权范围须评审后确定；未定义的跨系统自动操作不作为无限范围承诺。模型、工具、数据许可或写权限未就绪时，应标明对应能力未验收。

### 2.3 后续再考虑

- 超出首版字段清单的 PingCode 批量写入、工时／附件处理和复杂跨系统业务自动化，具体按后续场景评估。
- 自动代码评审、行级讨论及复杂 MR 分析视图。
- 人员／招聘等正式决策、未授权的跨系统操作，以及真实仪器控制、烧录、量产或生产发布。
- 日历时间块、投入时间观察、更灵活的周期任务。
- 跨设备同步、多人协作、离开工作台后的消息提醒。
- 只有实际使用证明必要，才扩展更细的人员或招聘流程。

## 3. 页面与日常使用

### 3.1 简化信息架构

| 入口 | 主要内容 |
| --- | --- |
| 今日 | 个人今日重点、待跟进；三个产线需关注的周重点偏差与风险 |
| 个人任务 | 汇集 PingCode 任务与 GitLab MR，显示来源、项目、编号、标题、来源状态、个人安排和最近同步时间；支持编号搜索及来源／项目／类型等筛选 |
| 个人任务内的 MR 视图 | 按待审、评审中、等待修改、待复查、已结束筛选；突出新提交、本人未处理行动及来源时效 |
| 管理 | 默认显示产线管理；另设其他管理事项分组 |
| 回顾 | 按周月选择成果、进展、偏差、风险及下期计划，使用 AI 生成有来源的草稿并人工编辑 |
| 提示词库 | 查看、搜索、新建、编辑、保存与复制个人常用提示词 |
| AI 执行记录 | 查看所关联任务、执行计划、授权范围、运行状态、工具操作、产物及核验结果，可从任务详情进入 |
| 设置 → 来源与同步 | 分别设置 PingCode、GitLab 的连接与同步规则，维护凭据、测试连接、启停同步，查看身份与权限提示 |

收件箱作为今日或任务列表中的待整理分组；来源与同步、模型配置、工具权限、备份和分类放在设置中。上述为信息组织建议，不要求每项都是独立页面，也不预设视觉风格。

### 3.2 日常使用方式

- **开始工作：** 查看或刷新 PingCode 任务及 GitLab 待审／待复查 MR，选个人今日重点，查看产线周重点异常和当天待跟进事项。
- **工作中：** 快速记新事项，复制常用提示词，按需让 AI 提出建议或在授权后执行任务；核对产物与结果，选择需要回写 PingCode 的内容；需要他人反馈时安排跟进。
- **结束工作：** 补充结果、阻塞和下一步，调整未完成事项。
- **每周：** 查看三个产线周重点结果、对应月目标的推进情况，以及下一周安排。
- **每月：** 回顾月重点交付、延期和风险，安排下月重点；按需要整理中心总结。

具体检查时间和频率待确认，不强制建立新的会议或填报制度。

## 4. 共用任务规则

### 4.1 分类与关联

主分类只使用“个人任务”或“管理”。分类按事项的主要目的确定，执行人另行记录：本人写中心总结仍属于管理，本人修复产线 Bug 属于个人任务。

同一任务只保存一份，可关联产线、项目、专题、人员或周期重点。在个人任务和产线重点中展示同一事项时，共享进展与结果，汇总不重复计数。

产线工作与本人行动可以关联但不混为一谈。例如“产线完成联调”由产线负责人推进，“本人协调测试资源”是关联的管理行动；协调完成不等于联调完成。

### 4.2 最少录入内容

| 场景 | 需要的信息 |
| --- | --- |
| 快速记录 | 标题；未分类时先进入收件箱 |
| PingCode 来源任务 | 任务编号、来源身份与项目、标题、原始页面链接、来源状态和最近成功同步时间；负责人、优先级、截止等按权限和实际字段获取 |
| GitLab 来源评审 | 来源实例、项目、MR 编号、标题、作者、评审相关人员、原始页面链接、MR 状态、当前提交版本和最近成功同步时间；字段以实际权限和版本为准 |
| 普通任务整理 | 主分类、下一步行动；日期、类型、执行人和关联对象按需填写 |
| 等待反馈 | 等待谁、等待什么、下次跟进日期 |
| 阻塞 | 阻塞原因、解除动作或求助对象、下次检查日期 |
| 产线重点 | 所属产线与周期、预期结果、负责人、计划节点、实际进展及反馈时间 |

计划处理日期、硬截止日期、对方承诺日期、下次跟进日期分别表达，不自动互相替代。无截止日期的任务也能正常使用。

### 4.3 状态与记录

本地任务与个人行动使用共用状态：收件箱、待处理、进行中、等待反馈、阻塞、已完成、已取消。PingCode 原始工作流状态、GitLab MR 外部状态和本人评审进展分别展示，不强制改成这套状态；个人行动结束不等于来源任务结束，MR 已合并也不等于本人已完成评审。

- 延期和逾期是日期提示，不增加另一套任务状态；调整截止日期保留原值和原因。
- 个人行动完成、验证通过、最终交付分别表达，不能把“代码修改完成”直接视为“已验证交付”。
- 已取消不计为完成成果；完成任务重开时保留原完成事实与重开记录。
- 重要结果、负责人反馈、计划变更保留发生时间、记录内容和必要来源。
- 归档收起历史记录，保留检索和关联；未完成事项归档时需明确后续安排。
- 首版以工作台内提示为主，完成或取消后停止行动提醒，不承诺关闭工作台后送达提醒。

### 4.4 PingCode 双向同步与个人安排

以下为基于用户已明确来源补充的候选规则；接入方式、拉取范围和刷新节奏仍待确认。

| 信息范围 | 内容与维护边界 |
| --- | --- |
| PingCode 来源信息 | 编号、标题、项目、原始状态，以及可读取的负责人、优先级、截止等；拉取更新来源快照，经确认的字段支持回写，不整条覆盖来源记录 |
| 工作台个人安排 | 今日重点、个人计划日期、个人排序、下一步、跟进日期、备注和产线／周期关联；由本人维护，刷新不得覆盖 |
| 来源与同步信息 | 来源组织／实例、项目及工作项身份、最后成功时间、拉取／回写结果、变更前后记录；用于识别来源、判断时效和核对结果 |

- 列表、详情、搜索和总结引用保留 PingCode 任务编号，并能打开原始页面；任务编号与工作台自身编号不能混淆。
- 去重优先采用来源组织／实例与工作项内部 ID 的组合，任务编号用于展示和查找。只有编号而尚未解析身份时，结合来源与项目进行核实，不跨组织仅凭编号或标题合并任务。
- 同一工作项重复拉取只更新同一记录；本地临时任务后续对应到 PingCode 时，经本人确认建立关联并保留已有记录，不再维护副本。
- 拉取范围建议先限本人负责及主动选定关注的事项；是否包含本人创建、参与或已完成任务，以及历史范围，后续确认，不默认拉取全组织资料。
- 首版支持主动刷新与可配置的定时拉取，实际频率待确认，不预设实时更新；显示进行中、成功或失败及最后成功时间，允许暂停定时同步。
- 外部断连、权限不足或部分数据未返回时，保留已保存信息和个人安排，明确标记状态；不能将“本次未拉到”视为已删除或已完成。
- 来源负责人变化、已确认归档／删除或移出拉取范围时，提示本人处理本地计划，保留已有历史与周期引用；不静默删除，不继续把旧快照展示为当前事实。
- 来源状态保留原名，未知状态不猜测映射；如需归并为待办／完成，须核实实际工作流后配置。本人结束一次行动不能自动把 PingCode 任务计为交付完成；来源关闭后也需检查剩余个人行动。
- 仅拉取工作所需字段；正文、自定义字段、附件及评论不默认全部复制。访问凭据不进入任务正文、普通备份或日志。

首版回写规则：

- 双向指“来源更新可读入，工作台选定变更可写回”，不代表每个本地字段都与来源自动互相覆盖。今日重点、个人计划、私人备注、产线周期关系默认只在工作台保存。
- 建议首批回写能力为任务状态更新和本人选定的进展评论；优先级、截止日期等是否纳入，以字段清单评审和本地版本验证为准。私密备注不自动当作评论发布。
- 回写前展示目标项目、任务编号、原值与新值或评论正文，由本人发起提交，或由已批准执行计划内的受限工具提交；实际允许字段与状态流转以来源权限和工作流为准。任务授权需覆盖目标、操作、字段和数据范围，不能只凭字段清单让 AI 自行改写。
- 写入前检查来源是否已有变更；有冲突时展示来源现值与本地建议，不采用默认“最后写入覆盖”。技术设计必须验证实际接口的并发保护能力，不能把单次先读后写宣称为无并发风险。
- 回写区分草稿／待提交、提交中、已确认成功、失败、结果待核实和冲突。收到成功响应后核对来源结果，再更新本地快照；失败不伪造来源状态，也不清除本地草稿。
- 超时或响应丢失时先核实来源再决定重试，避免重复状态变更或重复评论；重复点击同一次提交应保持单次效果。离线可保存草稿，重新连通后重新检查来源，不默认将过期草稿直接发出。
- 自动重试仅针对能够安全确认未生效或具备去重保障的操作，并可停止；不把不确定写入无限重发。记录提交人、目标、时间、变更范围和结果，不记录凭据。
- 双向回写纳入首版验收；若某必要字段缺少写权限、工作流不允许或接口无法提供可验证的保护措施，应明确该项限制及未验收状态，不静默降级为只读后宣称完成。

### 4.5 GitLab MR 拉取与评审跟进

- 来源已明确为公司内网本地部署的 GitLab。按确认的项目及本人评审职责拉取 MR，支持主动刷新及可配置的定时拉取；频率与提醒节奏待确认。
- 评审范围建议包含指派本人评审及本人主动选定关注的 MR；评审人、作者和 MR 负责人需要区分，不能仅筛选本人创建的 MR 来代替待审列表。实际分配规则与部署版本支持情况待核实。
- 列表显示来源项目、MR 编号、标题、作者、外部状态及最近同步时间，可打开内网原始页面；当前提交版本用于识别本人评审针对的内容。
- 本人评审进展至少区分待审、评审中、等待作者修改、待复查和已结束，并记录结论、未解决事项、已检查的提交版本与下一步。等待作者修改时安排跟进。
- 新拉取版本与本人已检查版本不一致时，保留原结论及其版本，提示重新复查；不能把旧版本结论直接沿用为当前版本已审。
- 同一实例、项目和 MR 身份重复拉取仅更新同一记录；不同项目的相同 MR 展示编号不得误合并。MR 与 PingCode 任务是不同来源对象，可建立关联但不合成同一条来源记录。
- 一项 PingCode 任务可以关联多个 MR，一个 MR 也可能服务多个事项；没有明确关系时允许暂不关联，不依赖标题相似自动绑定。汇总时区分代码评审行动与业务交付成果，避免重复计算。
- MR 合并、关闭、撤回评审安排或来源不可访问时，提示本人检查遗留计划；不自动标本人已评审，不静默丢弃备注、历史结论或产线周期引用。
- GitLab 与 PingCode 独立显示同步结果和最后成功时间；其中一处失败不影响另一处刷新及已保存的个人安排。无访问权限时如实提示，不绕过权限或把缺失记录当成已完成。
- MR 专项视图至少显示待审、评审中、等待作者修改、待复查与已结束，支持按项目、作者、更新时间筛选，并突出新提交与需复查原因；不要求跳出个人任务顶层入口。
- 首版只读取管理评审所需的 MR 元信息，不默认复制仓库源码、完整差异或全部讨论，不自动发表意见、批准或合并。

### 4.6 公司内网接入约束

两处数据源均为公司内网本地部署，这是已确认前提；工作台本身采用桌面应用还是公司内网网页仍待确定。

- 工作台负责拉取数据的运行端必须能通过公司允许的网络路径访问两处内网服务，原始链接也应在授权网络环境下打开；不默认它们可被公网服务直接访问。
- 不以申请公网暴露、配置外网转发或上传至第三方同步服务作为默认方案；如有特殊需求，再单独确认范围和授权。
- 接入前分别核实实际版本、接口可用性、组织／项目范围、本人身份映射、GitLab 读取权限、PingCode 读取及字段写入权限，以及内网域名解析、代理和证书信任要求。不能因公开文档存在某字段，就认定本地版本支持。
- 内网连接失败与登录／权限失败分别提示；内网证书问题按公司允许的信任方案处理，不默认跳过证书校验。
- 两处访问凭据独立管理，不写入任务、普通备份或日志；缓存、备注和导出仍属于公司内部资料。工作台部署与备份位置需符合公司制度，不因来源位于内网就默认允许向外传输。

### 4.7 AI 辅助与任务执行

AI 既可以提供拆解和总结，也可以通过工作台已接入的工具执行具体任务。模型负责理解与规划，执行器按权限调用工具，工作台记录过程并核验结果；只返回一段“已完成”的文字不算实际执行。

| 场景 | 输出或实际行动 | 使用方式 |
| --- | --- | --- |
| 任务拆解 | 建议子任务、预期结果／验收点、依赖和待澄清内容 | 编辑、选择后加入本地任务；如需向来源系统写入，进入单独授权流程 |
| 周月总结 | 依据所选事实形成成果、进展、偏差／风险、计划和需支持事项 | 保留来源，人工复核后复制或导出 |
| 查询与整理执行 | 读取授权范围内的任务／MR、汇集资料、建立本地跟进记录或生成并保存文件 | 在已批准的数据、工具和输出位置范围内执行，展示真实工具结果与产物 |
| PingCode 行动执行 | 通过允许的接口更新状态或发布选定进展 | 复用回写校验、冲突处理和结果核实；执行计划明确目标、操作与字段 |
| 本地项目执行（待确认场景） | 可能涉及读取工程、修改文件、运行脚本或测试 | 需确认是否纳入首版具体场景及允许工作区／命令，未确认时不默认开放通用命令执行 |

前两项需求明确；任务执行也是首版必需能力。表中执行用例为候选，需选定至少一个真实工具闭环作为首版验收场景；首批执行用例待明确，不能把全部候选视为默认操作权限。

执行规则：

- 发起任务时选择目标、关联任务、模型配置和允许材料，展示计划、拟用工具、可能写入的位置及成功条件。
- 可按单次任务授权明确的工具、项目、字段、目录和预算；已授权范围内连续执行，无须每一步重复确认。出现新增目标、越权操作或超出原授权的数据范围时暂停并说明原因。
- 工具必须预先注册并具有明确参数与返回结果；工作台校验目标、参数及权限，拒绝未知工具或不合规参数。模型回复本身不能获得新的工具权限。
- 状态至少区分待启动、计划中、待授权、执行中、已暂停、已完成、失败、部分完成、已取消和结果待核实；记录步骤、模型配置、调用结果、必要产物引用及核验结论。
- 成功条件基于实际工具回执、可读取的产物或预设检查；无法验证时标记待核实。过程和核验结果供本人复核，不直接作为正式验收证据。
- 支持停止后续步骤和查看部分结果；已发出的外部写入可能已经生效，需核实，不承诺取消即可撤销全部影响。重试复用回写去重和冲突机制。
- 来源正文、提示词引用材料和模型输出不构成额外授权，不得让其中的指令改变权限、切换到未许可模型或自行触发外部动作。
- GitLab 在本版仍只读，AI 不能发表意见、批准或合并；人员／录用正式决策、真实仪器控制、烧录、量产和生产发布不在执行范围。
- 模型、工具或内网服务不可用时，保留草稿、执行记录与已确认结果；人工工作仍可使用。占位回复、模拟接口或只有计划没有工具操作，不算任务执行验收通过。

### 4.8 模型与服务配置

首版支持以下三类接入；服务类型与具体模型分别配置，不固定某个模型版本。

| 接入类型 | 需要支持的配置 | 验证重点 |
| --- | --- | --- |
| 本地部署模型 | 公司或本人允许使用的模型服务地址、协议／适配方式、模型标识及实际需要的认证 | 从运行端实际连通并生成结果，确认上下文与工具调用能力；不假定所有本地模型支持同一接口 |
| DeepSeek 官方服务 | 官方 API 接入、API 凭据、模型标识及调用参数 | 通过官方 API 验证认证和调用；不采用官网网页自动操作或保存网页登录密码，API 权限与费用另行确认 |
| New API 部署 | 网关地址、网关令牌、网关提供的模型名称或别名及路由要求 | 验证实际网关版本、转发模型和工具调用兼容性，确认最终上游及数据流向 |

- 可保存多套有名称的连接配置，选择默认配置，并按任务选择或切换；本地部署的 New API 网关不代表最终模型也在本地，需记录实际路由和数据许可。
- 每套配置包括服务类型、地址、协议适配、模型、凭据引用、超时和必要参数；认证信息独立保护，不写入提示词、任务正文、普通备份或日志。
- 提供连接检查和实际模型调用检查，区分网络、认证、模型不可用、额度／限流和协议不兼容；返回错误时不显示为连接成功。
- 文本生成、结构化输出、工具调用等按实际测试记录能力。接入成功不代表工具执行能力也可用；不支持所需能力的模型不能被选为该执行任务的后端。
- 对需要工具调用的任务，验证模型提出调用、执行器执行、工具结果回传、后续结果生成这一完整闭环；不要仅根据模型名称或接口格式宣称兼容。
- AI 请求发起前可查看模型配置及选入材料范围；公司内网数据仅进入许可服务，默认排除人员／候选人敏感记录、私人备注、密钥、患者数据和未脱敏日志。
- 不因某服务失败而静默改投另一模型，尤其不自动从本地切换到外网。切换需满足原数据许可；执行中不静默改变模型、权限或预算，必要时暂停确认。
- 输入长度、调用次数、超时、执行步数与费用预算可设约束；实际服务不能提供的用量或费用信息标为未知或估算，不伪造精确数值。
- 三类接入均需用真实服务、虚构／脱敏材料验证；至少一个通过能力检测的模型完成代表性任务执行，其余配置按已测能力展示，不能把不支持工具的配置标成可执行。
- 所有生成内容保留使用的配置、时间与必要来源；事实、推断、建议分别表达，缺少证据时标待确认。

### 4.9 常用提示词库

目标是保存本人经常使用的提示词，编辑并保存后，下次打开能够直接复制使用；无需先连接或调用模型。

- 每条至少包含标题和正文，可选用途／标签；支持新建、查看、编辑、明确保存和按标题或正文搜索。
- 编辑保存后更新原记录并记录更新时间，重新打开读取最近成功保存的内容；未保存修改有清晰提示，保存失败保留输入。
- 提供复制正文入口，保留多行、缩进、特殊字符及占位符原文，不自动附带标题、格式包装或执行指令。
- 复制成功后给出反馈；剪贴板访问失败时明确提示并允许手工选择复制，不误报成功，也不因点击复制调用模型或执行任务。
- 提示词可用于外部工具；也可选择填入工作台 AI 指令，仍需单独选择模型、材料和执行授权。复制或使用提示词不自动覆盖原文。
- 提示词库随完整数据备份与恢复保存，模板中不存真实 API 密钥或账号密码；内容如含内部信息，按相同资料边界保护。

### 4.10 PingCode 与 GitLab 设置

两处来源均须提供可编辑、保存并重复使用的设置入口，内网地址、身份与项目不能写死在程序中。首版每类至少支持一套独立配置，不要求用户修改代码或配置文件才能连接自己的服务。

| 设置范围 | PingCode | GitLab |
| --- | --- | --- |
| 连接与身份 | 配置名称、内网服务地址、实际部署支持的认证方式与访问凭据；测试后显示可识别的当前账号／组织信息 | 配置名称、内网服务地址、实际部署支持的认证方式与访问凭据；测试后显示可识别的当前账号 |
| 拉取范围 | 组织／项目、本人负责或主动关注等筛选、历史范围；具体选项以实际接口为准 | 项目、本人评审或主动关注的 MR、状态及历史范围；具体选项以实际接口为准 |
| 同步规则 | 主动刷新、定时拉取开关和周期；工作流映射、允许回写字段与回写启用状态 | 主动刷新、定时拉取开关和周期；评审身份匹配、相关筛选，保持只读 |

- 支持查看、编辑、保存和停用配置；重启后保留最近保存的非敏感设置和受保护的凭据引用。必填缺失、地址格式错误或同步参数无效时给出具体提示，不清空已填内容。
- 连接测试使用当前编辑内容，明确标记“未保存配置的测试”或对应已保存版本；仅验证网络、认证及必要的读取能力，显示通过／失败、测试时间与可确认的身份。结果不足以确认写权限时明确标为未验证，不自动发表评论或修改任务来试写。
- 保存成功、读取测试通过、回写权限验证和同步启用分别表达。保存不代表连接成功，也不自动启动回写；读取通过不能认定 PingCode 已具备写权限，GitLab 设置中不开放写操作。
- 凭据默认遮蔽，编辑空值表示保留原凭据，清除或更换使用明确操作；禁止普通导出和日志记录明文。认证方式按实际部署适配，不要求在需求评审或聊天中提供真实凭据。
- 地址或凭据变更后，原连接结果标为需重测；不将原凭据自动发送到新地址。项目／范围变化需说明新增或移出的范围，已有记录与个人安排保留，不将未再拉到的任务删除。
- 核实地址修改属于同一实例地址调整还是切换新实例；新实例采用独立来源身份，不能仅靠任务／MR 展示编号合并。旧实例的待提交回写保留原目标并暂停，禁止随配置变更转写到新实例。
- 停用后停止新发起的定时拉取和回写，保留历史、关联及个人记录；已发出的请求继续按结果待核实规则处理。恢复启用需使用已保存且有效的配置。
- 超时、代理或内网证书信任等环境设置按需要放在高级项，不影响基本地址／凭据／项目的填写；不默认跳过证书校验。

## 5. 个人任务需求

个人任务是日常使用的主要入口，以内网 PingCode 来源的研发任务为核心，接入内网 GitLab MR 评审；平台提效与评审共用个人安排机制。

| 编号 | 需求 |
| --- | --- |
| P01 | 整理 PingCode 任务、GitLab MR 与少量本地任务，支持来源编号／标题搜索和来源、项目／专题、类型筛选；本地补充只填标题即可进入收件箱。 |
| P02 | 安排今日重点、个人计划日期与排序，独立保留 PingCode 来源优先级和截止日期；插单后可重新安排，来源刷新不覆盖个人安排。 |
| P03 | 功能和 Bug 可记录预期结果、阶段、下一步、阻塞及验证结论；复杂事项可拆解子任务，小任务不强制走完整流程。 |
| P04 | 平台提效和 AI 基建作为项目／专题管理，关联里程碑、行动和风险；区分环境部署、实际试用与效果，缺少证据时不默认提效目标达成。 |
| P05 | GitLab MR 同步与专项视图：在确认的内网项目及评审范围内主动／定时刷新，展示项目、编号、标题、作者、外部状态及链接；按本人评审进展筛选和跟进，不自动将已合并记为本人已评审。 |
| P06 | PingCode 拉取：在授权和确认范围内主动／定时获取任务，展示任务编号、原始页面及来源状态；所需字段和状态映射在接入前核实。 |
| P07 | 身份与关联：分别按 PingCode 工作项、GitLab MR 的来源身份更新去重；本地绑定保留已有安排，PingCode 与 MR 可关联但不合并，关联产线月周重点不产生来源副本。 |
| P08 | 同步边界与异常：来源信息和个人安排分开保存，两处独立记录同步结果及时效；断连、权限变化和数据缺失时保留本地内容，显示异常且不误判完成或删除。 |
| P09 | MR 版本与复查：区分外部状态、本人评审进展与已检查提交版本；新版本到达时提示复查，保留旧结论的适用版本，MR 结束或评审安排变化时检查遗留行动。 |
| P10 | PingCode 回写：支持确认范围内的状态更新和选定进展评论，字段清单及权限待验证；由本人提交或在明确授权的 AI 执行计划内提交，保留变更与结果，私人安排不自动回写。 |
| P11 | 同步与回写可靠性：支持定时拉取暂停／恢复、变更识别、冲突提示、写入结果核实及安全重试；不静默覆盖来源变更，不重复发表评论，不将结果不确定显示为成功。 |

首版所有 P 编号均为核心范围。GitLab 同步、MR 专项视图、新提交识别与 PingCode 双向回写纳入首版；代码内容的实际评审继续在公司 GitLab 完成，不要求工作台成为代码评审编辑器或引入 AI 自动评审。

## 6. 管理需求

### 6.1 产线管理：管理侧重点

三个产线均有负责人，工作台帮助本人掌握重点与偏差，不接管负责人日常排程。首版由本人记录计划和反馈，不要求负责人增加账号或重复填写全部任务。

| 编号 | 需求 |
| --- | --- |
| M01 | 三产线概览：可配置名称和负责人，显示当月重点、本周重点、关键偏差、风险、本人需协调事项和最后更新时间。 |
| M02 | 月重点：按产线和月份登记重点、预期交付／验收标准、负责人、计划节点；对照查看实际进展、偏差、关联周重点和月末结果。 |
| M03 | 周重点：登记本周预期阶段结果、计划日期、负责人和实际进展；可关联月重点，也允许独立临时重点并注明原因。 |
| M04 | 进展与介入：记录反馈时间和来源，对照预期结果显示正常、需关注、已延期或待确认；明确未完成原因、修正计划及需要本人协调的行动。 |
| M05 | 调整与结转：保留原计划及调整原因，未完成任务可延续到下周／下月；新周期保存独立计划记录，原周期未完成事实不被覆盖。 |
| M06 | 风险与问题：记录影响、等级、责任人、应对、复查日期；发生后保留转化为问题的历史，关闭时记录依据和残余影响。完成处置行动不自动关闭风险。 |

月周重点的关键规则：

- 月重点看目标交付，周重点看阶段结果。完成若干周任务，不代表月目标已满足验收要求。
- 同一任务可被月、周重点引用，执行进展共用；各周期的预期结果、反馈和调整记录分别保留。
- 一周跨越两个月时保留实际起止日期，可关联不同月重点，汇总按事实去重。
- 结转表示继续推进，不能自动计为上期完成；原承诺、偏差和新安排均可追溯。
- 用阶段结果、实际进展与反馈说明完成情况，不强制填写主观百分比，也不简单平均周任务进度来计算月目标完成度。
- 反馈缺失或过时显示待确认；计划节点已过且目标未达成时提示延期；本人决定是否介入或升级，不自动对外通知。
- 跨产线共同依赖统一关联，避免同一资源或组件问题被分散重复记录。

补充边界：

- 中心总结不能把本人的台账自动视为完整中心数据，需要收集的同事材料显式列出。
- 月总结不简单拼接周报；区分周阶段结果与月目标完成，保留结转和未完成情况。
- 人工补充无来源的材料标为待核对；AI 建议／总结为需复核草稿，执行结果另有真实回执和核验，不能将模型声称完成或缺少来源的内容自动记为事实。
- 普通汇报导出与完整备份分开；完整备份可能包含敏感信息，不应默认共享。
- 不将内部代码、患者数据、密钥、未脱敏日志或招聘隐私写入任务正文或发送至未经批准的服务。
- 部署、设备和数据规模未确定，性能目标与存储保护方案在技术设计阶段补齐，不把未测指标写成已满足。
